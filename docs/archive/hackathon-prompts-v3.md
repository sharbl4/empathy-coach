# «Между строк»: полноценная v1 за 3 дня

Версия 3. Полноценная v1 за три дня, облачный хостинг от организаторов, LLM — GigaChat. Заменяет предыдущий план MVP.
Команда: Антон — team lead / Codex; Дима — backend / Codex; Даня — frontend / Claude Code.

Цель — опубликованное приложение, которым новый пользователь может пользоваться самостоятельно. Три дня — план параллельной работы команды, а не гарантия срока. Если часть кода уже написана, сначала сравнить её с этим планом и сохранить подходящие решения.

## 1. Объём готового продукта

1. Регистрация, подтверждение email, вход, выход, восстановление пароля.
2. Короткий онбординг с объяснением возможностей и неопределённости трактовок.
3. Ввод сообщения, отношений с собеседником, контекста и цели ответа.
4. «Сначала твоя версия»: предполагаемые эмоции, точные цитаты-сигналы, вариант «не понимаю».
5. Разбор: буквальный смысл, 2–3 возможные трактовки, эмоции и потребности, основания, неопределённость, уточняющий вопрос, сравнение с гипотезой пользователя.
6. Черновик ответа и обратная связь по конкретным фразам; улучшенный вариант и примеры под четыре цели: поддержать, уточнить, помириться, обозначить границу.
7. Упражнение по ситуации на 30–60 секунд, попытка пользователя и обратная связь.
8. Ролевая тренировка: три ответа пользователя, естественные реплики собеседника, итоговый разбор; возможность завершить раньше.
9. Сохранение завершённых шагов, история разборов, поиск по названию, продолжение после перезагрузки и повторного входа.
10. Прогресс: число разобранных ситуаций, завершённых упражнений и диалогов, практикуемые навыки, последний совет. Без выдуманного «процента эмпатии».
11. Настройки имени, удаление отдельных разборов и всех своих учебных данных с подтверждением.
12. Адаптивный интерфейс, обработка ошибок, повтор после сбоя, реальная модель, база данных, GitHub, CI и публичный HTTPS-адрес.

Все пять ранее предложенных учебных механик обязательны. Упражнение и роль доступны после разбора, проходить их каждый раз необязательно. Черновик предлагается до готовых примеров, есть кнопка «Нужен пример».

Граница v1: без оплаты, нативных приложений, интеграций с мессенджерами, голоса, OCR, социальных функций и диагностики. Новые функции требуют решения Антона и пересмотра срока.

Критерий результата: новый человек по ссылке регистрируется, использует своё сообщение, проходит практику, закрывает браузер, возвращается к сохранённой работе. Другой пользователь не может открыть его данные. Приложение работает независимо от ноутбуков команды.

## 2. Архитектура

Предлагаемый стек: TypeScript, npm workspaces, React + Vite, Fastify, Zod, PostgreSQL, pg и SQL-миграции. Аккаунты — Supabase Auth; для PostgreSQL можно использовать тот же Supabase-проект. По решению команды LLM — GigaChat API через серверный GigaChatProvider. Дима проверяет доступные в аккаунте модели и бюджет, имя задаётся GIGACHAT_MODEL. Codex и Claude Code остаются инструментами разработки команды.

```text
Браузер → Supabase Auth: регистрация / вход / recovery
   │
   └── /api + access token
          │
       Fastify: проверка токена и владельца данных
          ├── PostgreSQL: разборы, результаты, практика
          └── AiProvider → GigaChatProvider → GigaChat API
```

- Browser SDK Supabase используется для Auth; учебные данные доступны только через backend.
- Backend проверяет токен через Supabase auth.getUser(token), получает проверенный userId и проверяет владельца каждого объекта. userId из body не используется для авторизации. Недоступность Auth не разрешает обход проверки.
- Учебные таблицы находятся в непубличной схеме app, не выставленной через Supabase Data API. Клиентским ролям нет доступа к ней. DATABASE_URL — только на сервере. SQL параметризованный.
- Production: backend отдаёт web/dist и /api с одного origin. Разработка: Vite proxy.
- Один backend-процесс, без микросервисов, Redis, отдельной очереди и многоагентного оркестратора. Постоянная истина — PostgreSQL.
- MockProvider нужен для тестов и явно обозначенного резервного демо. Пользовательский production-путь работает с живой моделью. Ошибка live не подменяется фикстурой.
- SQL-мигратор хранит применённые версии, использует блокировку и транзакции, где допустимо. Применённые миграции не переписываются.

```text
/
  AGENTS.md
  CLAUDE.md
  README.md
  package.json
  package-lock.json
  .env.example
  Dockerfile
  compose.yaml
  apps/web/src/{app,components,features,lib}/
  apps/api/src/{auth,routes,services,repositories,ai,db}/
  apps/api/migrations/
  apps/api/test/
  packages/contracts/src/{schemas,fixtures}/
  docs/{product,architecture,api,acceptance,deploy,demo}.md
  .github/workflows/ci.yml
```

Совместимые версии фиксируются lockfile в начале. Версия Node — в репозитории. После первого дня стек не меняем.

### Облачный хостинг от организаторов

Антон подтвердил: проект разрешат развернуть на облачном хостинге. Используем его как основную площадку и выкладываем первый рабочий сценарий уже в день 1. Провайдер, ресурсы и способ доступа пока неизвестны; наличие выделенного сервера, Docker или управляемой БД не предполагаем без проверки.

В начале Антон узнаёт у организаторов:

- Что выдают: виртуальную машину, контейнерную платформу или хостинг с ограниченным временем выполнения запросов?
- Как выкладывать приложение: через GitHub, образ контейнера или SSH? Как задать секреты окружения?
- Есть ли PostgreSQL, постоянное хранилище, резервные копии и ограничения подключений?
- Есть ли HTTPS-адрес, как назначается PORT, доступны ли логи и перезапуск?
- Разрешены ли исходящие запросы к Supabase/Auth, GigaChat API, endpoint получения его токена и почтовому сервису?
- Каковы CPU/RAM, срок жизни площадки и лимиты? Требуют ли правила хранить БД именно на этой площадке?

Основной вариант для VM или постоянно работающего контейнера: единое приложение web + api, внешняя PostgreSQL, HTTPS и один backend-процесс. Предложенная фоновая обработка runs рассчитана на постоянно работающий процесс. Если доступна только serverless-площадка, не запускать там фоновые задачи после HTTP-ответа без поддержки платформы: до реализации runs согласовать с Антоном поддерживаемый механизм задач либо размещение backend на постоянном процессе.

Если организаторы предоставляют PostgreSQL, используем её при подходящих условиях. Supabase Auth может работать отдельно от этой БД. Если БД не выдают и правила разрешают внешнюю, используем PostgreSQL Supabase. Не хранить production-данные только в файловой системе контейнера.

Сначала выясняем параметры предоставленной площадки; отдельный платный хостинг не покупаем по умолчанию. Доступность внешних сервисов и ресурсные лимиты проверяем на реальном развёртывании в день 1.

Server env: DATABASE_URL, SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, GIGACHAT_CREDENTIALS, GIGACHAT_SCOPE, GIGACHAT_MODEL, GIGACHAT_BASE_URL, AI_PROVIDER, PORT, APP_ORIGIN, NODE_ENV. AI_PROVIDER=gigachat для живого режима, mock — только явно выбранное тестирование/демо. GIGACHAT_CREDENTIALS — Authorization Key из проекта GigaChat API, не пароль от веб-чата и не краткоживущий access token.
Browser env: VITE_SUPABASE_URL, VITE_SUPABASE_PUBLISHABLE_KEY — публичные настройки. Ключ модели, DB credentials и административные ключи запрещены в VITE_* и клиентской сборке.

Отдельные dev/test/prod. Тесты и seed не запускаются на production-БД. Тестовый AuthVerifier разрешён только как тестовый адаптер, production отказывается запускаться с ним.

В первые часы Антон проверяет GitHub, Supabase, redirect URLs, отправку писем и хостинг. Дима — первый реальный запрос модели и лимиты. Подписки coding-инструментов не считаем настроенным серверным API-доступом. Секреты не передавать в чат.

Регистрация и recovery должны доставлять письма новым пользователям, а не только владельцу проекта. Проверить ограничения почтового сервиса и при необходимости настроить доступный SMTP. Внешние аккаунты, доступность сервиса и оплату не считать готовыми без проверки.

## 3. Данные и сохранение

| Таблица | Основные поля |
|---|---|
| profiles | id = Auth userId, display_name, onboarding_completed_at, created_at |
| sessions | id, user_id, title, situation JSONB, guess JSONB, revision, created_at, updated_at |
| ai_runs | id, session_id, user_id, revision, kind, status, input JSONB, output JSONB, prompt_version, error_code, idempotency_key, created_at, updated_at |
| roleplays | id, session_id, user_id, revision, status, turn_count, feedback JSONB, created_at, updated_at |
| roleplay_messages | id, roleplay_id, sequence, role, content, created_at |
| practice_events | id, user_id, session_id, source_run_id/source_roleplay_id, kind, skill, created_at |

Situation: message, relationship, context, goal. Goal: support | clarify | reconcile | boundary.
UserGuess: emotions[], evidenceQuotes[], unsure. Цитаты — подстроки message; допустимы пустые массивы и «не понимаю».
Run kind: analysis | reply_feedback | reply_examples | exercise | exercise_feedback | roleplay_start | roleplay_turn | roleplay_feedback.
Run status: pending | succeeded | failed. Только валидированный успешный output становится результатом шага.

Индексы: sessions(user_id, updated_at), ai_runs(session_id, revision, kind); уникальность user_id + idempotency_key; roleplay_messages(roleplay_id, sequence); уникальность источника practice_events. Время в БД — UTC, показ локальный.

Изменение исходных данных увеличивает revision. Старые результаты не подмешиваются в новую работу. UI v1 может показывать только текущую версию без отдельного экрана версий. Просмотр четырёх примеров не изменяет исходную цель сессии.

Прогресс считается по уникальным успешным событиям; повтор запроса не увеличивает счётчик. Удаление сессии удаляет её результаты, сообщения и события. «Удалить учебные данные» очищает данные приложения, сохраняя аккаунт; UI прямо объясняет этот объём. Не называем это полным удалением Auth-аккаунта.

Переписки не помещаем в localStorage, аналитику и логи. Auth SDK отдельно управляет входом по документированной конфигурации. Перед отправкой — небольшая подсказка убрать личные данные. Не обещаем удаления у внешнего API-провайдера и из резервных копий без проверки его правил.

## 4. Контракт API — зафиксировать до параллельной работы

Источник истины — Zod-схемы packages/contracts. docs/api.md содержит соответствующие JSON-примеры. Первоначальный контракт создаёт Антон; дальнейшие изменения согласуются с ним. Дима и Даня не создают копии DTO.

Публичные: GET /api/health/live и GET /api/health/ready (БД с таймаутом, без платного вызова модели). Auth-формы работают через Supabase SDK. Остальные endpoint требуют Bearer access token.

| Endpoint | Назначение |
|---|---|
| GET /api/me | профиль, возможности, режим AI |
| PATCH /api/me | имя, завершение онбординга |
| DELETE /api/me/data | удалить свои учебные данные |
| POST /api/sessions | сохранить ситуацию и гипотезу |
| GET /api/sessions?cursor=&limit=&q= | история и поиск по названию, limit ≤ 50 |
| GET /api/sessions/:id | текущие данные, результаты и роль |
| PATCH /api/sessions/:id | обновить входные данные с expectedRevision |
| DELETE /api/sessions/:id | удалить сессию и зависимые записи |
| POST /api/sessions/:id/analyze | создать run анализа |
| POST /api/sessions/:id/reply-feedback | создать run отзыва; body: draft |
| POST /api/sessions/:id/reply-examples | создать run четырёх примеров |
| POST /api/sessions/:id/exercise | создать run упражнения |
| POST /api/sessions/:id/exercise-feedback | body: exerciseRunId, answer |
| POST /api/sessions/:id/roleplays | создать роль и run первой реплики |
| POST /api/roleplays/:id/turns | body: content; история берётся из БД |
| POST /api/roleplays/:id/finish | создать run итогового разбора |
| GET /api/runs/:id | статус и валидированный результат |
| GET /api/progress | счётчики, навыки, последний совет |

### Runs и повтор запросов

- Все AI POST принимают expectedRevision и Idempotency-Key. Ключ создаётся один раз на намерение и сохраняется при сетевом повторе.
- POST сохраняет pending-run и возвращает 202 {runId, resourceId?}. UI опрашивает GET /runs/:id раз в 1–2 секунды до succeeded/failed; при уходе прекращает опрос. Детали сессии позволяют восстановить ожидание после refresh.
- Задача запускается внутри единственного backend-процесса: таймаут, лимит на пользователя, общий concurrency cap. Не накапливать неограниченную очередь.
- Один внешний вызов модели на run. При неизвестном исходе автоматического повторного платного вызова нет. Повтор failed-run — новое намерение и ключ. Старый ключ возвращает прежний run; новый payload с тем же ключом — конфликт.
- Pending-run переживает рестарт в БД. При старте backend незавершённые run прошлого процесса переводятся в failed/RUN_INTERRUPTED. Пользователь может повторить; не обещаем продолжить потерянный API-вызов.
- Одна активная AI-операция на сессию. Редактирование/удаление этой сессии во время pending — конфликт. Удаление всех данных логически отменяет pending-run; поздний output не восстанавливает записи.
- Сервер проверяет владельца, revision и предыдущий шаг. Чужой/старый exerciseRunId недопустим.
- Roleplay хранится и считается сервером; клиент не задаёт историю и роли. После третьего пользовательского ответа генерируется итог. Ранний finish доступен после первого ответа.
- Добавление хода и run защищено транзакцией/блокировкой. При failed-генерации новый run отвечает к уже сохранённой реплике, не дублируя её. Антон фиксирует в контракте явный retry endpoint для failed roleplay-run: POST /api/runs/:id/retry с новым Idempotency-Key; остальные failed-run можно повторить тем же действием с новым ключом.
- Внешний вызов модели вне длительной SQL-транзакции. Сохранение результата проверяет актуальность run, revision и наличие сессии.

### Форматы результатов

Analysis: literalMeaning; interpretations[2..3] с emotion, possibleNeed, explanation, evidenceQuotes[]; uncertainty; clarifyingQuestion; guessFeedback; skillTip.
ReplyFeedback: strengths[], phraseFeedback[] с quote/possibleImpact/suggestion, revisedReply, options[4].
ReplyOption: goal, text, explanation — по одному на каждую цель.
Exercise: instruction, skill, exampleHint; идентификатор — id run.
ExerciseFeedback: strengths[], improvement, suggestedAttempt.
RoleplayOutput: kind=message с content либо kind=feedback с strengths[], improvements[], nextPractice. Счётчик и завершение контролирует сервер.
Progress: analyzedSessions, completedExercises, completedRoleplays, skills[] с числом практик, latestTip.

Размеры: message 1–6000 символов, relationship 1–200, context 0–4000, draft/answer/roleplay content 1–3000, до 3 эмоций и цитат в гипотезе. Ограничить также output модели и размеры массивов.

Ошибка: {error:{code,message,requestId}}. HTTP: 400 VALIDATION_ERROR; 401 UNAUTHORIZED; 404 NOT_FOUND (также чужой объект); 409 REVISION_CONFLICT/OPERATION_IN_PROGRESS/IDEMPOTENCY_CONFLICT; 429 RATE_LIMITED; 503 DEPENDENCY_UNAVAILABLE. AI-сбой — failed-run с безопасным errorCode. Без ключей, сырых ответов модели и stack trace.

Фикстуры: три вымышленные ситуации, все виды результатов, pending/failed/succeeded, пустая и заполненная история/прогресс. Примеры проходят схемы в CI.

Это рабочие ориентиры, не требование работать 72 часа без отдыха. Если рабочих часов меньше, пересчитайте план сразу. Каждые несколько часов — сверка: что в main, блокеры и следующий проверяемый результат.

| Этап | Антон | Дима | Даня | Результат |
|---|---|---|---|---|
| День 1, первые 2–3 часа | repo, сервисы, schemas, фикстуры, scaffold | проверка модели/Auth/БД, SQL-модель | структура экранов | контракт принят, доступы проверены |
| День 1, середина | CI, staging, env | миграции, Auth, CRUD, runs | Auth, кабинет, история, форма | два аккаунта изолированы |

| День 2, первая половина | ревью и E2E | отзывы, примеры, упражнение | черновик, отзывы, упражнение | обучение работает |
| День 2, вторая половина | интеграция и регрессия | роль, прогресс, удаление | роль, прогресс, настройки, resume | весь объём в main |

Конец дня 1: вход, сохранённая сессия и живой анализ по внешнему URL. Если этого нет, прекращаем улучшать оформление и исправляем интеграцию.
Конец дня 2: все функции доступны по HTTP, нет экранов «скоро». Крупные модули не оставляем на третий день.
После release candidate функции не добавляем. При нехватке времени упрощаем оформление и анимации, сохраняя согласованный объём.

## 18. GigaChat: обязательные детали интеграции

Выбор GigaChat не меняет контракт frontend/backend. Все особенности сервиса изолированы в apps/api/src/ai/GigaChatProvider. Дане не нужно подключать GigaChat SDK или получать ключ модели.

### Авторизация и доступ

- Authorization Key используется для получения access token; запросы модели авторизуются токеном. Согласно документации, токен действует 30 минут. Сервер кеширует его и обновляет до истечения с небольшим запасом, корректно обрабатывая expires_at по фактическому контракту API.
- Одновременные запросы ждут одно обновление токена. Не запрашивать новый токен на каждый анализ.
- GIGACHAT_SCOPE берётся из типа доступа аккаунта; не угадывать его по названию команды. Используются значения GIGACHAT_API_PERS, GIGACHAT_API_B2B или GIGACHAT_API_CORP согласно выданному доступу.
- URL модели и авторизации сверяются отдельно по официальным docs: нельзя считать их одним endpoint. Для нового подключения документация указывает API-хост https://api.giga.chat; выбранную версию пути фиксируем в GIGACHAT_BASE_URL.
- Без credentials backend сообщает ошибку конфигурации. Токены, Authorization Key и заголовки авторизации не выводятся в лог.

Источник: [авторизация GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api), [получение токена](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-token).

### Структурированные результаты

- Используем response_format с type=json_schema, схемой и strict=true. В схеме явно задаём required. В API v1 response_format находится на верхнем уровне запроса; в v2 — в model_options. Выбираем одну версию и проверяем реальный запрос, не смешиваем форматы.
- JSON Schema генерируем из общих схем, если это поддерживает закреплённая версия Zod, либо проверяем соответствие схем тестом. Не переносим параметры другого провайдера по памяти.
- Модель возвращает JSON как текст: разбираем его и валидируем Zod до сохранения succeeded. Отдельно обрабатываем завершение по лимиту и отказ сервиса.
- Если выбранная модель/версия не принимает схему, это выясняется первым live-запросом. Дима согласует рабочую модель/версию, а не молча убирает валидацию.

Источник: [структурированные данные GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/structured-output).

### Облако, сертификаты и проверки

- Используем официальный JS/TS SDK gigachat либо прямой REST; дополнительный оркестратор для этого не нужен. Проверяем доверие TLS из реального контейнера на хостинге. Если нужен дополнительный доверенный CA, устанавливаем его по официальной инструкции. Не отключаем проверку TLS и не задаём NODE_TLS_REJECT_UNAUTHORIZED=0.
- В день 1 проверяем из облака: получение токена → доступная модель → короткий анализ → валидный JSON. До завершения регистрации UI эта проверка доступна Диме отдельно.
- Добавляем тесты адаптера: истечение токена, несколько одновременных refresh, ошибка авторизации, лимит/429, timeout, отказ, повреждённый JSON, неправильная схема. Тесты не расходуют живые токены.
- Сохраняем правило runs: без скрытых повторных вызовов генерации при неизвестном исходе. Обновление токена заранее не является повтором генерации.
- Лимиты параллельности и расхода настраиваем под фактически выданную квоту GigaChat. Наличие SDK не подтверждает наличие бюджета аккаунта.

Источник: [официальный JS/TS SDK GigaChat](https://developers.sber.ru/docs/ru/gigachain/tools/js/gigachat).
