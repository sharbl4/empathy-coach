# Политика информационной безопасности «Между строк»

> TELEGRAM-ONLY 31.10.2026: старые строки о Supabase/browser/PR#9 описывают прежний аудит. Актуальные обязательные меры — private sender→verified domain context, ownership/revision, одноразовые SMTP-коды, один poller с lease, local-only model без reasoning/логов, Tailscale ACL и Windows firewall. Источники правил защиты/инцидентов/удаления ниже сохраняют силу; статусы прежней реализации не подтверждают новую. См. ../architecture.md и ../acceptance.md.

Версия 0.1 от 31.10.2026. **Внутренний проект требований.** Утверждает оператор Неделько Антон. Контакт для сообщений об уязвимостях: antonnedelko@outlook.com. Не направлять на этот адрес реальные переписки, секреты и выгрузки БД; сначала прислать безопасное описание и согласовать канал.

## 1. Ответственность и оценка

Антон ведёт перечень обработок/доступов, инфраструктуру и реагирование; Дима отвечает за API/БД, Даня — за клиент в рамках согласованных задач. Доступ к данным не следует автоматически из доступа к GitHub. Каждый участник получает минимальные права и обязательства конфиденциальности; после окончания работ доступ отзывается.

До публичной эксплуатации описать ИСПДн, оценить вред субъектам, актуальные угрозы и уровень защищённости по постановлению № 1119, выбрать применимые меры по ст. 19 152-ФЗ и приказу ФСТЭК № 21. При применении СКЗИ отдельно определить требования ФСБ. Не объявлять произвольно «УЗ-4», «сертифицировано» или «152-ФЗ выполнен» по наличию TLS/Docker.

## 2. Обязательные меры

| Область | Требование | Проверенный статус |
|---|---|---|
| Идентификация | Веб-токен проверяется backend через Supabase getUser; ID владельца из тела не используется; Auth outage закрывает доступ | Есть в коде; реальные DB/ownership-тесты обязательны |
| Доступ к данным | Проверять владельца и revision для всех ссылок, включая вложенные run/roleplay ID; параметризованные SQL; app-схема недоступна клиенту напрямую | Есть в архитектуре/API; production-права нужно подтвердить |
| Изоляция клиента | Очистка или изоляция черновиков при смене аккаунта, expiry, logout; результаты одного пользователя не показываются другому | Отдельный review-блокер PR #9, не объявлен исправленным |
| Транспорт | Публичный HTTPS, проверка TLS, корректные CA; никаких NODE_TLS_REJECT_UNAUTHORIZED=0, insecure fetch или обхода Auth в production | TLS-проверка предусмотрена; публичного хостинга пока нет |
| Секреты | Секреты только в env/secret store backend, не в Git/клиенте; отдельные dev/prod; минимальные права, отзыв/ротация при компрометации, MFA админов | .env игнорируется; настройки аккаунтов и хостинга требуют проверки |
| Журналы | Не логировать переписки, ответы модели, body, Authorization, пароли, Telegram updates, bot token, ключи и callback URL с токенами; безопасные коды и request ID по необходимости | Fastify logger=false; reverse proxy, Auth, БД, APM и облачные логи отдельно не проверены |
| Модель | Текст — недоверенные данные, не команды; фиксированные инструкции; строгая схема и проверка цитат; отсутствие tools с доступом к секретам; один вызов/run без скрытого платного retry | Есть в backend; это не защита от всех атак и не автоматическое обезличивание |
| Браузер | Auth-сессия SDK содержит чувствительные токены: предотвращать XSS, не передавать их в аналитику; строгие redirects, безопасная обработка callback; CSP/заголовки проверить на хостинге | Сохранение сессии включено; production-заголовки не подтверждены |
| БД и backup | Закрытая сеть, отдельные роли, ограниченный админ-доступ, защита дисков/копий по оценке угроз, документированное место в РФ; тест восстановления и повторное применение удалений | Локальный PostgreSQL работает; production и backup не настроены |
| Обновления | Закреплённые зависимости, обязательный CI, проверка реальных DB-тестов без skips; оценка уязвимостей и контроль изменений | Есть CI; он не доказывает правовое соответствие и работу живых внешних сервисов |

## 3. Требования к будущему Telegram-боту

Бот пока отсутствует; перечисленное — задача проектирования, а не функции, обещанные пользователю.

- Только личные чаты. Группы, inline, контакты, геопозиция, файлы и бизнес-подключения не включаются без отдельного решения оператора. Не собирать полный update «для отладки».
- При webhook проверять X-Telegram-Bot-Api-Secret-Token до обработки. Bot token и webhook secret — разные секреты, только на backend. Не писать URL Bot API с токеном в HTTP-логи. HTTPS и ограничение размера/частоты запросов обязательны.
- Не доверять произвольному userId/chatId из публичного HTTP. Использовать поля только из проверенного канала Telegram; Mini App/initData и account linking требуют отдельного корректного протокола, а не доверия username. Username изменяем и не является идентификатором владельца.
- Дедуплицировать update и пользовательское намерение до сохранения/генерации, проверять владельца результата и адресата ответа, ограничивать квоту и параллельность. Повтор webhook не должен вызывать дополнительный платный run.
- До согласия — только информация, выбор и необходимое краткоживущее состояние. Не вызывать GigaChat с входным текстом. Неподдерживаемый контент не пересылать в модель. Хранить доказательство согласия с ограниченным доступом.
- Реализовать отзыв и удаление с проверкой аккаунта, понятным объёмом операции и подтверждением результата. Очистить связку Telegram/account, исключить позднее восстановление при завершении run. Удаление данных сервиса не выдавать за удаление всех сообщений в Telegram.
- Публиковать собственную политику в @BotFather и давать доступ к ней без анализа/регистрации. Перед анализом напоминать удалить идентификаторы; предупреждение не заменяет законное основание и техническую минимизацию.

## 4. Хранение, обращения, уничтожение

Перед запуском утвердить реестр: набор/цель, основание, место, доступ, срок/условие окончания, обработчик, метод и доказательство уничтожения. Для журналов, обращений, согласий и backup — отдельные обоснованные сроки и проверяемые процедуры; не назначать всем данным единый бессрочный срок.

Учебное удаление реализовано в PostgreSQL, но не является процедурой удаления Auth-аккаунта и профиля. Полный сценарий должен охватывать все хранилища и порученных обработчиков. Backup не использовать для обычного доступа к удалённым данным; при восстановлении до выдачи пользователям повторно применить удаления. Нельзя обещать удаление у провайдера без договорного и технического подтверждения.

Сведения по запросу субъекта предоставляются по ст. 20. Прекращение/исправление/блокирование — по ст. 21. Если нет возможности уничтожить данные в обычный срок, применяется предусмотренный законом порядок блокирования и последующего уничтожения, а не произвольное продление. Подтверждение уничтожения оформить по приказу РКН № 179; хранить предусмотренные им подтверждающие материалы, не сами удалённые переписки.

## 5. Инциденты

При обнаружении утечки или компрометации ответственный сразу фиксирует время выявления, ограничивает затронутую обработку, отзывает ключи/сессии при необходимости и сохраняет минимальные доказательства в закрытом доступе. Не вставляет исходные данные в GitHub issues, чат команды или общедоступный отчёт.

Оператор устанавливает состав, причины и масштаб инцидента. При факте неправомерной/случайной передачи или доступа, нарушивших права субъектов, уведомляет Роскомнадзор: первоначально в течение 24 часов с момента выявления, результаты внутреннего расследования — в течение 72 часов с того же момента. Это не два последовательных срока. Обязательные сведения и способ подачи сверить по ст. 21 ч. 3.1 и [порталу инцидентов РКН](https://pd.rkn.gov.ru/incidents/form/).

Отдельно выполнить необходимые обращения к обработчикам и информирование затронутых пользователей с учётом закона и фактического риска. Восстановление допускается после устранения причины, проверки доступов/изоляции и подтверждения, что удалённые данные не возвращены. Провести разбор и зафиксировать меры без публикации содержимого сообщений.

## 6. Контроль перед релизом

Lead фиксирует доказательства выполнения мер, полный live-путь и отдельные проверки безопасности/удаления на вымышленных данных. Контроль включает два аккаунта, чужие ID, logout/expiry, согласие/отказ/отзыв, повтор update, квоты, отсутствие чувствительных данных в логах, удаление и восстановление. Положительный CI, работоспособность локального Docker и текст этой политики не заменяют проверку настроенного production.
