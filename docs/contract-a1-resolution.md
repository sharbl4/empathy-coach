## Email recovery: chosen signatures

All user methods take domain-issued ctx and strict input; writes additionally take UUID intent:
- emailVerification(ctx,{}) → EmailVerificationStatus (read DB, never send email).
- requestEmailCode(ctx,{email},key) → EmailVerificationStatus.
- resendEmailCode(ctx,{challengeId},key) → EmailVerificationStatus.
- verifyEmailCode(ctx,{challengeId,code},key) → EmailVerificationResult {account,verification}.

Status: state none / verified / challenge. Challenge contains challengeId, state sending/sent/delivery_unknown/failed/expired/locked, maskedEmail (first≤2characters+***@domain), expiresAt, resendAfter, attemptsRemaining0..5. No code/code hash/full address in this DTO. Verify input keeps six-digit code; owner always ctx, challenge ID is only an owned resource reference.
The domain returns the latest challenge from DB, independently of Dialogue TTL/process memory. Bot/web read this status on onboarding resume, restart and after CODE_INVALID/CODE_EXPIRED or a resend. Do not store authoritative challenge ID/email only in a Map or callback. Verify returns account and status from one consistent DB transaction.
10min TTL,60s resend cooldown,5 attempts and existing account/address hourly caps remain. A new request/resend atomically invalidates the old code and creates a NEW challengeId. Resend reads the target address from its owned prior challenge; caller cannot supply another address/owner. Concurrent verify/resend lock the account+current challenge; stale challenge fails, never verifies a replacement code accidentally. Changing address is requestEmailCode with a new intent.
Idempotency namespaces request/resend/verify separately; same intent+same payload never sends twice or consumes another attempt. Different payload conflicts. Rate-limit/attempt state is DB-backed and survives restarts. SMTP happens outside DB transactions. SMTP failure is honest; crash after possible send is delivery_unknown and never auto-resends. Explicit resend after cooldown gets a new intent. Processing intents require bounded reconciliation, never a permanent OPERATION_IN_PROGRESS latch.
Exact error selection: foreign/missing challenge → NOT_FOUND; owned superseded challenge → REVISION_CONFLICT; expired verify → CODE_EXPIRED; wrong code/locked/failed challenge → CODE_INVALID; still sending → OPERATION_IN_PROGRESS with no attempt consumed. A reconciled delivery_unknown may verify a received correct code until TTL; preserve its HMAC until consume/expiry, never resend automatically. Status prefers an active replacement target over the previous verified address. Successful verify returns only verified=true; wrong/expired attempts throw a safe error after committing the attempt state. Resend with no pending target after verification is a verified no-op and sends no mail. Invalidated old IDs are not the active status. Consumed code material is erased; already verified status has no old challenge. Account deletion/consent withdrawal blocks sending/late results and cleans pending code material under the retention policy.

## DomainError and inbox failure

One runtime class: DomainError({code,requestId,retryAfterSeconds?}) exported from /product. DomainFailure is the exact safe payload; HTTP uses ProductError={error:DomainFailure} and HttpErrorStatus. Same code enum in DomainErrorCode/ProductErrorCode (one value alias). Do not copy a local error class/enum into adapters. Never serialize Error.stack/message/cause, SQL/SMTP errors or a raw model response.
normalizeDomainError(unknown,requestId) returns INTERNAL_ERROR with no raw details. An unknown code/Error is NOT a retryable dependency error. Only vetted infrastructure adapters classify a known temporary failure as DEPENDENCY_UNAVAILABLE. Root exception mapping must not convert every bug/validation/unknown error to that code.
domainRetryPolicy allows bounded read/exact durable intent replay only for OPERATION_IN_PROGRESS/RATE_LIMITED/DEPENDENCY_UNAVAILABLE. Max3 total attempts; counters and nextAttemptAt are persisted across process restarts, not a bot Map. INTERNAL_ERROR and unknown errors are terminal. generation never auto-retries. Delivery retries do not create runs. A fresh user retry is an explicit action with its own intention.
claimUpdate returns UpdateReceiptV2 with durable intentKey/status/attempts/nextAttemptAt/failure. recordUpdateFailure(ctx,{updateId,failure},key) atomically stores retry_wait (known eligible failure, attempts<3) or failed (unknown/terminal/budget exhausted). An explicit step claim, not each read/repeated failure report, increments attempts. Repeated reporting key is idempotent.
acknowledgeUpdate only advances the cursor after a known completed operation or persisted terminal failure; it must NOT turn failed into completed. Unknown outcome from a mutating transaction first reconciles the SAME domain intent. If terminal state cannot be recorded, stop/drain the affected processing path and surface unhealthy/operator action; do not silently ack or invent success. No raw update logging or promise of replay beyond transport retention. Accepted user input belongs in durable FSM/intent/outbox before ack; Telegram redelivery is not permanent storage.

## Auth exchange, cookies and HTTP

Bot issueWebLink(ctx,key) → private IssuedWebLink on exact WEB_ORIGIN/auth/connect#token=...; preview disabled, do-not-forward warning. GET/HEAD never redeem. Landing removes fragment immediately, no-store/no-referrer, no third-party scripts; only explicit POST /api/auth/web-links/redeem {token,confirmed:true} exchanges it. Token/session secrets never localStorage, query, logs or public response JSON.
openBrowser(bindingCookie?,sessionCookie?) issues opaque BrowserContext and PublicWebSession/CSRF. Before EVERY mutation HTTP calls authorizeWebMutation(browser,{origin,csrfToken}) and verifies IdempotencyRequestHeaders (origin/idempotency-key/x-csrf-token). Includes anonymous-bound exchange. Resolve account through resolveWebSession only; cookie values are server-side parameters, never body authority. Recheck account/session at the operation transaction and before model/delivery success.
authApi + authBindings bind session/entry/exchange/logout/list/revoke-one/revoke-all to facade methods. All auth mutations require Origin+CSRF+intent, no wildcard CORS. Logout/revocation clears the current cookie as indicated in bindings. Deleting an owned current session clears it too; revoking another session keeps the current one. Telegram can list/revoke its own sessions directly through domain context.
webCookiePolicy fixes names/attributes: production __Host-between-session / __Host-between-link, Secure+HttpOnly+Path=/+SameSite=Lax, NO Domain attribute. HTTP dev/test uses separate names. TTL24h absolute,2h idle, update last activity only after actual valid session access; replay does not extend/revive revoked/expired sessions. Single-session revocation, revoke-all, consent withdrawal and account deletion recheck live authorization; revoke-all also invalidates outstanding login links.
Hashes only for stored login/session tokens. Same browser+same exchange intent may recover the same session receipt safely (HMAC derivation/protected receipt), not create a second session. Different browser/payload/reused token conflicts. An already authenticated DIFFERENT account yields ACCOUNT_CONFLICT before consuming/revoking anything; user must explicitly log out. No email/username merge.
Exactly one trusted reverse-proxy IP list; not trustProxy=true. Sensitive request/URL/headers and HTTP error logs disabled/redacted at source, response only safe ProductError. Reject path/query/body collisions; validate shared request and public response schemas. authBindings is the executable mapping, no parallel hand-written auth DTOs.

## Complete sanitized preview and stable intention

createPreview accepts only PreviewSource; all owned session/roleplay/run/card references are checked. Domain persists the full sanitized outgoing user snapshot, including draft, context, evidence, exercise answer and complete role turns. No hidden original text may be rebuilt after confirmation. Mask email/phone in every field, expose every outgoing user field; editable IDs are server-issued.
Preview includes dependencies with revisions/contentVersion, modelRevision, promptVersion, templateHash, complete ordered fields and token budget. Field IDs are unique, turn references exist and order is deterministic. editPreview may change only editable owned fields; re-mask, advance revision/hash and invalidate old confirmation.
confirmPreview(ctx,{id,expectedRevision,snapshotHash},key) → expiring PreviewReceipt. startRun(ctx,{previewId,previewRevision,snapshotHash,expectedSessionRevision},key) requires the exact confirmed DB snapshot, fits budget, non-expiry and unchanged dependencies/model/prompt/template. retry also requires the matching confirmed hash. PREVIEW_NOT_CONFIRMED/PREVIEW_STALE are explicit errors, not OPERATION_IN_PROGRESS.
Hash covers the canonical sanitized request, dependencies and model/prompt/template version. Unedited unknown/too-large budget cannot generate. One run gets exactly that immutable snapshot; no hidden repair or inference retry. Only strict output/evidence validation permits succeeded; model reasoning/invalid/refused/truncated outputs fail.
For creation/edit idempotency hash the canonical STRICT validated ORIGINAL intention with HMAC before lossy masking; two different emails/texts collapsing to the same masked string are still different intentions and must conflict under one key. Do not store raw input in logs/idempotency metadata to achieve this.
Editing/deletion/revocation and role-turn changes invalidate stale receipts and late output; a new field confirmation cannot silently authorize a different snapshot. Privacy confirmations inserted directly by tests are NOT a public confirmation API.

## Single lifecycle

scripts/application.mjs is the only production entrypoint: identify bot → createDomain ONCE → acquirePollerLease(botId) → domain.start ONCE → HTTP.listen → telegram.start(domain,lease). Construction/import never acquires a bot lease, starts timers/workers, polling or listening.
The bot factory exports createTelegramTransport; no createDomain import, process signal handler or alternative production main in its import graph. One polling loop and one delivery loop started by that adapter; domain.start owns model queue/maintenance/reminder scheduler, never Telegram HTTP sends. HTTP and bot receive the SAME ProductFacade object.
Domain must work with ProductOptions (not old DomainOptions.botId); TransportState can receive bot identity when acquirePollerLease runs. stopAccepting and all closes are idempotent. Root stops accepting, polling/delivery and HTTP, drains/aborts workers/model, releases lease/pool under the shared110s deadline; grace120s. start() twice cannot create duplicate workers, close/partial-start tests must cover this.
Do not gate read-only domain data on GPU availability or an unrelated poller-lease check. Losing the required app lease does trigger shared shutdown. Keep one execution permit until the real generation promise settles, even if the request times out/deletes.
