# Решение Антона: contracts 0.2.0 · создание сессии

Согласовано Антоном в задании review frontend #8/#9 от 30.10.2026. Это отдельное изменение протокола, не исправление контрактов внутри PR участника. До реализации backend и frontend версия не считается интегрированной.

POST /api/sessions требует Bearer и Idempotency-Key UUID. Body SessionInput и ответ Session не меняются. Отсутствующий/невалидный ключ — 400 VALIDATION_ERROR. Операция — экспортированная константа CREATE_SESSION_OPERATION=session.create.

| Условие | Результат |
|---|---|
| Новый (проверенный userId, session.create, key) | Атомарно сохранить сессию и привязку ключа; 201 Session |
| Тот же scope/key и тот же нормализованный body | 201, тот же id; вернуть текущую сохранённую сессию, не перезаписывать её |
| Тот же scope/key, другой нормализованный body | 409 IDEMPOTENCY_CONFLICT; не создавать/не менять сессию |
| Тот же UUID ключа другого пользователя | Независимая сессия; никаких чужих данных |
| Тот же UUID ключа в AI-операции | Не конфликтует с session.create; существующие AI retry-правила не переписываются этим изменением |
| Исходная сессия уже удалена | 404 NOT_FOUND для старого ключа, без восстановления; новый разбор требует нового ключа |

Сравнивать результат SessionInput.parse: фиксированный порядок полей схемы и сохранённые значения, включая порядок массивов. Пробелы, которые схема не нормализует (например context), остаются данными. Не хешировать произвольный порядок ключей сырого JSON и не принимать hash/userId от клиента.
При повторе после PATCH возвращается тот же ресурс с его текущей revision, исходный body его не откатывает. Проверка привязки исходного payload выполняется по серверному receipt, а не сравнением с текущей ситуацией.

Дима выбирает SQL-реализацию: уникальность user/operation/key и транзакция session+receipt с блокировкой при гонке. Недостаточно SELECT перед INSERT без уникального ограничения. При rollback не оставлять завершённый ключ без сессии. Хранить hash/ID и техническую привязку, не вторую копию переписки. На удаление сохранять минимальный tombstone ключа без текста/результата/hash переписки, чтобы старый сетевой повтор не восстановил удалённое; 404 после удаления имеет приоритет над payload comparison. Для самого нового пользовательского намерения клиент создаёт новый UUID.

Это не фоновая очередь и не вызов модели. Ключи переживают restart, внешний вызов при создании не нужен. Миграции пишет Дима новым SQL-файлом; применённые миграции не менять. При clear учебных данных удалить сессии/результаты и чувствительные receipts, сохранив только минимальную техническую защиту от replay.

## Приёмка backend на отдельной PostgreSQL

Один последовательный и несколько конкурентных одинаковых POST → один id/одна строка. Конкурентные разные payload с одним ключом → один успех и один 409. Два пользователя с одинаковым ключом независимы. Переупорядоченный JSON с теми же нормализованными данными повторяется; другое значение конфликтует. Тот же ключ можно использовать для analyze без конфликта с create. Повтор после restart возвращает ту же сессию. После PATCH не перезаписывает данные, после DELETE/clear не воскрешает. Ошибки проходят ApiError. Без ключа/с плохим ключом — 400.

## Frontend #9

createSession(body, idempotencyKey) требует ключ явно, валидирует общую headers-схему и передаёт его HTTP-транспорту. UUID создаётся один раз на намерение; повтор после timeout/network/неизвестного исхода сохраняет ключ и данные. Изменение payload/новое намерение создаёт новый ключ; успешное сохранение очищает намерение. Ключ хранится рядом с черновиком только в памяти вкладки и изолируется по владельцу; чужой аккаунт не должен получить старый текст или намерение после expiry/relogin.
Не писать учебный текст/ключи в localStorage или логи. Auth SDK управляет своей сессией отдельно. Тест потери ответа после успешного INSERT должен повторить HTTP с тем же ключом и показать один разбор в истории.

## Порядок интеграции

Отдельный contract PR → backend PR Димы, основанный на contract-ветке → адаптация #9 Даней → общий CI и реальные DB-тесты → последовательное слияние совместимых частей → live-путь. Не утверждать новую серверную семантику по одному зелёному тесту Zod. Дублирующий POST checkpoint выполняется до генерации и обязан вернуть тот же id.
